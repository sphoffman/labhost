# LabHost v1.5 Development Test Guide

This document describes the **development** image only. It does not replace the
stable `1.4` or `latest` tags.

Development image:

```text
ghcr.io/sphoffman/labhost:1.5-dev8
```

The validation workflow publishes that tag only after shell, image-build,
endpoint-discovery, endpoint-default, service-runtime, NTP-query, RADIUS, and
persistence checks pass.

## Current v1.5-dev8 scope

### Unified managed endpoints

The client-oriented helpers discover three endpoint roles:

- `clN` synthetic clients created by `clients-create`
- `pp-*-pc` PC endpoints created by the PC/phone abstraction
- dynamically learned phone voice endpoints from authoritative PC/phone state

Useful commands:

```bash
clients-list
clients-list --pcs
clients-list --phones
clients-list --clients
clients-status --all
clients-ping 192.0.2.1 --pcs
clients-arp --phones
```

Synthetic client, PC, and tagged phone child interfaces default to MTU 1500
even when their underlying LabHost dataplane parent remains jumbo-capable.
Synthetic PC/phone child interfaces also use `arp_ignore=1` and
`arp_announce=2`, matching the existing independent-host behavior of `clN`
clients.

### Endpoint-aware traffic and iperf

```bash
iperf-client 192.0.2.20 --interface pp-eth1-pc
iperf-udp 192.0.2.20 100M --interface pp-eth2-pc
iperf-reverse 192.0.2.20 --interface pp-eth3-pc
iperf-bidir 192.0.2.20 --interface pp-eth4-pc
iperf-parallel 192.0.2.20 4 --interface pp-eth5-pc
clients-iperf 192.0.2.20 --pcs
path-test 192.0.2.1 --interface pp-eth1-pc
```

`iperf-* --help` and `lab-help iperf-*` now display the endpoint-aware syntax,
including `--interface <iface>`.

`clients-iperf` runs selected endpoints sequentially in this development build.
A concurrent aggregate mode is deferred so multi-stream iperf is not confused
with multi-endpoint traffic.

### IPv4 helper semantics

Static `ip-set` is replacement-oriented. For example:

```bash
ip-set eth1 10.10.10.20/24
```

leaves `10.10.10.20/24` as the interface's global IPv4 address instead of
silently retaining an unrelated prior static address. DHCP behavior is
unchanged.

### Lightweight services

All new services are stopped by default.

NTP:

```bash
ntp-server-start
ntp-server-start --bind eth1
ntp-server-status
ntp-query 192.0.2.10
ntp-server-stop
```

NTP uses chronyd with `-x`; it never adjusts the container/host kernel clock.
`ntp-query` uses a single-sample chrony query (`maxsamples 1`) so a one-shot
verification completes deterministically. CI verifies an actual NTP response.

Syslog:

```bash
syslog-server-start --udp
syslog-server-start --bind eth1 --both
syslog-server-status
syslog-tail
syslog-send 192.0.2.10 "labhost test"
syslog-server-stop
```

SNMP agent and traps:

```bash
snmp-server-start --bind eth1 --community public
snmp-server-status
snmp-trap-listen --bind eth1
snmp-trap-tail
snmp-trap-stop
snmp-server-stop
```

RADIUS:

```bash
radius-client-add switch1 192.0.2.2 testing123
radius-user-add labuser labpass
radius-server-start --bind eth1
radius-server-status
radius-log
radius-server-stop
```

`radius-server-start --bind <interface|ip>` resolves the requested LabHost
endpoint and constrains the FreeRADIUS listeners to that address. CI verifies the
bound listener and an actual Access-Accept.

## Persistence

Service starts and RADIUS/SNMP configuration are stored as working intent under
`/run/labhost/intents/services`.

`lab-save` generates the complete startup configuration as the invoking user and
uses controlled self-elevation only for the write into `/config`. This allows the
normal unprivileged `lab` SSH user to save through a root-owned bind mount without
requiring a matching `lab` user or UID on the Containerlab host. The saved startup
file and `.bak` are written as `root:root` mode `0755`. CI exercises this against
an actual root-owned bind-mounted directory.

Saved `mtu-set clN ...` commands are deferred until after `clients-create`, so
startup replay never references a synthetic client before it exists. Deliberate
non-default synthetic-client MTUs are preserved. CI deletes and recreates a
saved synthetic client from generated startup to verify this ordering.

RADIUS client/user configuration is always emitted before
`radius-server-start` so startup replay reconstructs the complete authentication
database before FreeRADIUS starts. `lab-reset` stops and purges v1.5 service
runtime/unsaved intent before executing the existing reset core.

Because service commands are ordinary startup commands, configured SNMP
communities, RADIUS client secrets, and RADIUS test-user passwords will be stored
in the saved startup script. Use lab/test credentials only.

### Development topology persistence test

`labhost-v1.5-dev.clab.yml` bind-mounts the tracked
`labhost-v1.5-dev-configs/` directory to `/config` on both test hosts. Generated
`*.sh` files in that directory are ignored by Git.

After configuring a host:

```bash
lab-save
```

Restart it with Containerlab, not Docker directly:

```bash
containerlab restart -t labhost-v1.5-dev.clab.yml --node host2
```

Containerlab parks and restores veth dataplane interfaces during its lifecycle
restart. A plain `docker restart` is not a valid persistence test for a Linux
Containerlab node because Docker does not preserve the non-`eth0` veth links.

A stronger recreation test is:

```bash
containerlab redeploy -t labhost-v1.5-dev.clab.yml
```

Do not add `--cleanup` when the intent is to preserve the lab directory and saved
state.

## Deferred work

The following are not release blockers for v1.5 and can be evaluated in later
work:

- DNS record-management helpers
- DHCPv6 and router-advertisement helpers
- wired 802.1X supplicant validation
- concurrent multi-endpoint iperf mode

The NCE topology TCP-checksum/performance investigation is also being tracked
separately because a simple LabHost-to-LabHost Containerlab control path passed
at roughly 19 Gbit/s with zero TCP retransmissions, and the NCE issue persisted
when synthetic macvlan endpoints were bypassed.

## Stable-image safety

Do not retag `1.5-dev8` as `latest` and do not replace `1.4` in an important lab
until the development tests are satisfactory. The stable `1.4` and `latest`
images remain the production choice during v1.5 development.
